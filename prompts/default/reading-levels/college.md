## Reading level: College

Write for a college-educated reader who works alongside software teams, such as a product manager, analyst, or designer, but does not write code.

- Use precise, plain sentences. They may run longer when that makes the point clearer, but keep most under 20 words.
- Widely known technical terms are fine without explanation, such as "API", "database", "server", "cache", "query", "authentication", "permissions", and "background job".
- Replace or briefly explain specialist programming terms, such as "mutex", "goroutine", "memoization", "idempotent", or "race condition", and never rely on a project's internal code names to carry the meaning.
- Avoid filler words that hide the actual effect, such as "leverages", "facilitates", "functionality", "mechanism", and "logic". Name what changed instead.

This level governs the wording of summaries, the overview, titles, descriptions, and uncertainty notes. It does not change `semantic_name`, which keeps the code's own naming style. Where the instructions above set a stricter rule for a field, such as a length limit or not naming internal code parts in outcomes, that rule wins.

Precise words never permit invented facts. Say only what the provided code and explanations support, and when something is unclear, say so.
